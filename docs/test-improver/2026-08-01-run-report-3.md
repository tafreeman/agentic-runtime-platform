## 2. The defect: `CoderAgent` could not handle C++

`_extract_code_blocks` interpolated the caller-supplied language straight into
a regex:

```python
pattern = rf"```(?:{language}|{language.lower()})?\s*\n(.*?)```"
```

`CodeGenerationInput.language` is `min_length=1` with a lowercasing validator —
**any** string reaches this line. Two consequences, both confirmed by running
the shipped code:

**a. `c++` silently never matched.** Since Python 3.11, `c++` is a valid
*possessive quantifier*, so no error is raised — the pattern just becomes
"one-or-more `c`, possessively" and can never match the literal text `c++`.
`_extract_code_blocks` returned `[]` for a correctly-fenced C++ response, so
`_is_task_complete` never fired, so `BaseAgent._execute_loop` burned all five
iterations and `run()` raised:

```
RuntimeError: Agent reached max iterations (5) without completing task
```

On Python ≤ 3.10 the same expression is `re.error: multiple repeat` instead —
so this also silently changed shape when the repo moved to 3.11.

**b. Punctuated names raised `re.error` out of the execution loop.**
`c(`, `a)b`, `[x`, `*a`, `\` and friends escape as an unhandled `re.error`
from inside `_is_task_complete`.

**Fix applied** (`agentic_v2/agents/coder.py`, 1 line of behaviour + comment):

```python
lang = re.escape(language)
pattern = rf"```(?:{lang}|{lang.lower()})?\s*\n(.*?)```"
```

Verified strictly non-regressive against the previous behaviour: `python`,
`typescript`, `javascript`, `rust`, `go`, `c#`, `f#`, `objective-c`,
bare fences, multi-fence documents and the mismatched-language negative case
all produce identical results before and after; `c++`/`C++` change from `[]`
to extracted; every metacharacter name changes from `re.error` to `[]`.

**Why it survived:** `tests/test_agents.py::TestCoderAgent` has exactly one
`_extract_code_blocks` test and it passes `"python"` — the one language whose
name contains no regex metacharacter and which also happens to be what the
backend-less stub emits.

## 5. Findings flagged, not fixed

1. **The generic fence pattern misses punctuated language tags.** With no
   `language` argument the pattern is ` ```(?:\w+)? `, which cannot match
   ` ```c++ `, ` ```c# ` or ` ```objective-c `. `refine()` is the only caller
   that omits the language, so **refining C++/C#/Objective-C code silently
   returns `success=False, code=""`** even though `run()` now handles those
   languages fine. Fixing it means broadening what counts as a fence info
   string repo-wide — a maintainer call, so it is pinned as characterisation.
2. **`_extract_code_fallback` can emit unparseable code.** The collected block
   is joined and then `.strip()`-ed *as a whole*, so only the first line is
   dedented. For a block whose lines share one indent level the result is an
   `IndentationError` — pinned with an explicit `compile()` assertion. Worse,
   `_parse_output` reports that output as `success=True, confidence=0.9`: the
   same confidence a clean fenced extraction gets, despite being the
   lower-trust heuristic. A `textwrap.dedent` and a distinct fallback
   confidence would both be small changes, but both alter returned values.
3. **The `Here's` preamble strip requires the apostrophe.** The regex is
   `^Here\'s?\s*(the\s+)?` — the apostrophe is mandatory and the `s` optional,
   so `"Here is the code"` and `"Heres"` pass through untouched while a bare
   `"Here'"` would be stripped. Almost certainly the inverse of the intent.
4. **The backend-less stub is Python-only.** `_call_model`'s canned response is
   a hard-coded ` ```python ` fence, and `_is_task_complete` is language-aware,
   so a keyless `run()` for any other language raises after five iterations.
   This means the no-API-key baseline (`AGENTIC_NO_LLM=1`, the `no-llm-smoke`
   CI job) only ever exercises `CoderAgent` for Python — and it is a live trap
   for anyone writing a backend-less test in another language. Pinned.
5. **Dead code in `_call_model`.** The
   `for msg in reversed(messages): if msg.get("role") == "user": break` loop
   has no body effect and no use of `msg` afterwards. Same category as July's
   backlog item 2.
