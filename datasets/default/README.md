# datasets/default — scored golden eval dataset

This directory holds the COMMITTED golden dataset consumed by the deterministic,
key-free CI gate `scripts/eval_gate.py` (CI job `eval-golden-gate` in
`.github/workflows/eval-package-ci.yml`, mocked path — see also the label/nightly
`--live` real-model gate documented in that workflow file). It satisfies the
audit's scored-eval finding: the gate scores a committed golden through the real
`agentic_v2_eval.Scorer` and fails the build when the weighted rubric score
drops below the committed threshold.

## Files

- `golden_cases.json` — the dataset manifest. One case per scored golden output,
  covering 4 of the platform's 6 shipped workflow types (`code_review`,
  `bug_resolution`, `consensus_review`, `fullstack_generation`). Fields:
  `case_id`, `rubric` (a packaged `agentic_v2_eval` rubric name),
  `golden_output_path` (resolved relative to this directory),
  `expected_criteria` (expected step names / success rate / max retries used by
  the derivation), and `threshold` (per-case pass bar in `[0, 1]`; see the
  per-case notes below — `bug_resolution`/`consensus_review`/`fullstack_generation`
  sit at 0.80 because that is their achievable ceiling under the `code` rubric,
  not a loosened bar).
- `code_review_output.json` — a verbatim copy of
  `agentic-workflows-v2/tests/golden/code_review_output.json`, the `code_review`
  workflow result captured under `AGENTIC_NO_LLM=1` (all steps `success`, no
  retries, placeholder LLM outputs). The gate scores this snapshot; it does NOT
  re-run the workflow engine — `agentic-workflows-v2/tests/test_golden_workflow.py`
  remains the engine-regression detector. The two are complementary.
- `bug_resolution_output.json` — `bug_resolution` workflow result captured under
  `AGENTIC_NO_LLM=1` with `resolution_depth="standard"` (both `when:`-gated steps
  active). All 5 steps `success`, no retries.
- `consensus_review_output.json` — `consensus_review` workflow result captured
  under `AGENTIC_NO_LLM=1`. Exercises a different DAG shape than `code_review`:
  three parallel reviewer steps, a tier-0 deterministic majority-vote aggregator,
  and a `when:` gate on a *step output* (`steps.vote.outputs.meets_threshold`)
  rather than an input. All 5 steps `success`, no retries.
- `fullstack_generation_output.json` — `fullstack_generation` workflow result
  captured under `AGENTIC_NO_LLM=1`. The largest DAG in the dataset (8 steps):
  architecture design, parallel backend/frontend/migration generation,
  integration tests, review, a `when:`-gated rework pass, and final assembly.
  All 8 steps `success`, no retries.

Each `*_output.json` was generated by actually running the named workflow through
the real engine under `AGENTIC_NO_LLM=1` and stripping volatile keys (see
"Regenerating the golden" below) — none of these were hand-authored or
hand-computed. `conditional_branching` and `iterative_review` (the other 2 of
the platform's 6 shipped workflow types) are intentionally not yet represented:
`conditional_branching` currently has a `when:`-evaluation gap under this same
`AGENTIC_NO_LLM=1` path (a compound `and` clause across two distinct `inputs.*`
references evaluates `False` when it should be `True`, tracked as a separate
engine fix) that would make its golden non-representative of intended behavior
until fixed.

## How scoring works (deterministic, no API key)

`scripts/eval_gate.py` derives the `code` rubric's five criteria from stable
structural fields of the golden output (no LLM, no randomness, no wall-clock):

| Criterion (weight) | Derivation |
|--------------------|------------|
| Correctness (0.30) | `success_rate / 100.0` |
| Completeness (0.20) | fraction of `expected_step_names` whose step `status == "success"` |
| Code Quality (0.20) | fraction of required `code_metrics` keys present on `parse_code` |
| Efficiency (0.15) | retry penalty: `1.0` when `total_retries == 0` |
| Security (0.15) | `1.0` unless any step leaks a non-empty `error_type` |

The derived floats are scored by `Scorer(load_rubric("code")).score(...)`; the
gate asserts `missing_criteria == []` (a typo'd criterion name is a hard fail,
not a silent denominator shrink) and then compares `weighted_score` to the
effective threshold (`max(--threshold, the case's own threshold)` — note this
means a case's own `threshold` can only ever *tighten* the bar, never loosen it
below what `--threshold` passes on the command line).

Note: Code Quality scores key PRESENCE (schema), not value magnitude — the
golden's metrics are legitimately `0` for empty input code, so this criterion
catches a dropped-key schema regression, not a code-quality-of-input change.
**Important caveat:** the derivation looks for `code_metrics` specifically on a
step literally named `parse_code`. Only `code_review` has such a step, so every
other case in this dataset scores Code Quality `0.0` by construction — this is a
known structural limitation of `derive_criteria()` (it was written for
`code_review`'s shape first), not a defect in `bug_resolution`,
`consensus_review`, or `fullstack_generation`'s actual output. Their 0.80
thresholds are each case's achievable ceiling (1.0 on all four other criteria),
not a loosened bar. Widening `derive_criteria()` to recognize other workflows'
equivalent steps (e.g. `bug_resolution`'s `triage`) is a legitimate follow-up,
but out of scope here — the criterion derivation is deliberately not touched
without also verifying every existing case's score doesn't silently change.

## Threshold

Committed at **0.80** for `code_review`, `bug_resolution`, `consensus_review`,
and `fullstack_generation` (the runner default and the value the CI step passes
via `--threshold`). Only `code_review`'s unregressed golden scores **1.0**; the
other three cap at **0.80** for the Code Quality reason above. 0.80 is above the
`code` rubric's own `thresholds.pass: 0.75` and catches any single
heavy-criterion regression to zero (e.g. Correctness → 0 on `code_review` yields
0.70 < 0.80).

## Server-side golden resolution (second consumer)

Since ADR-044, the FastAPI server's dataset loader
(`agentic_v2/server/datasets.py`) ALSO consumes `golden_output_path` when a
sample from this (or any local) dataset is selected for a scored run or a
replay re-evaluation. Its rules deliberately differ from `eval_gate.py`'s:

- The path resolves **relative to the dataset JSON file** and must stay under
  an allowed dataset root (tenant dir or the fixture/evaluation roots) —
  absolute paths and `..` escapes are rejected. `eval_gate.py` has no such
  confinement.
- The golden is reduced to its `final_output` subtree, null-stripped, and
  inlined into the sample as `golden_output_text` for token-overlap scoring —
  `eval_gate.py` instead consumes the full envelope structurally.
- Failures (missing/unreadable/oversized/non-UTF-8 file, empty golden
  content) never fail the load: the sample loads without the golden and the
  reason is recorded as `golden_output_error` in the dataset metadata (and
  `rehydration_error` on replay).

A case that passes the CI gate can therefore still degrade server-side (or
vice versa). Converging the two resolvers is planned with the ADR-042
evalkit migration; until then this section is the contract for the server
half.

## Regenerating a golden (deliberate only)

Never hand-edit the golden JSON. To update `<workflow>_output.json`:

1. Run the workflow through the real engine under `AGENTIC_NO_LLM=1`, exactly as
   `agentic-workflows-v2/tests/test_golden_workflow.py` does for `code_review`
   (`WorkflowLoader().load(name)` → `get_registry().get_adapter("native")` →
   `engine.execute(workflow, ctx=ExecutionContext(...), input_data=...)`), then
   strip the same volatile keys that test strips (`start_time`, `end_time`,
   `workflow_id`, `total_duration_ms`, `duration_ms`) before dumping to JSON.
   For `code_review` specifically, regenerate
   `agentic-workflows-v2/tests/golden/code_review_output.json` via its documented
   `--update-golden` flow first, then copy it here — it remains the single
   source of truth for that case (see the "Files" note above).
2. Save the result to `datasets/default/<workflow>_output.json`.
3. Re-run the gate locally
   (`AGENTIC_NO_LLM=1 python scripts/eval_gate.py --cases datasets/default/golden_cases.json --threshold 0.80`)
   and adjust `expected_criteria`/`threshold` by PR only if the score
   legitimately changed — never to paper over an unexplained regression.
